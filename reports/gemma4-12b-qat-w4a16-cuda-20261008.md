# Gemma 4 12B QAT 실행 확인

## 결론과 실행 환경

`google/gemma-4-12B-it-qat-w4a16-ct`는 이 Windows 머신에서 oev의 기본 CUDA 로더로 로딩되지만, 첫 추론의 전체 BF16 역양자화 중 CUDA OOM이 발생합니다. 압축 가중치를 유지하고 현재 Linear 층만 임시 BF16으로 풀어 계산하는 진단 경로에서는 18건 모두 완료됐습니다. 기본 oev 로더를 수정한 결과가 아니라 별도 실험용 실행 방식의 결과입니다.

- 실행일: 2026-10-08 (Asia/Seoul).
- Windows, NVIDIA GeForce RTX 4050 Laptop GPU, 전용 VRAM 6GB, Windows 공유 GPU 메모리 사용.
- Python 3.11, PyTorch `2.14.0+cu130`, Transformers `5.17.0`, Accelerate `1.15.0`, compressed-tensors `0.16.0`.
- [Google 배포 체크포인트](https://huggingface.co/google/gemma-4-12B-it-qat-w4a16-ct/tree/1d2c2d7f2466070e69d6fb3fd5ce9a7d75f2f6ee): 리비전 `1d2c2d7f2466070e69d6fb3fd5ce9a7d75f2f6ee`.
- 다운로드: 10,264,229,896바이트. SHA-256 `60b6e3989502969d8ae04185d72ecbbc7db63978d5af747a493d53895aa6bfa3`를 Hugging Face LFS 메타데이터와 대조해 일치를 확인했습니다.
- 모델 클래스: `Gemma4UnifiedForConditionalGeneration`. 현재 설치된 `AutoModelForCausalLM` 매핑이 지원합니다.
- 메타 장치에서 설정으로 계산한 파라미터 수: 11,959,730,176개, BF16 가중치 약 22.277GiB. 실제 활성값/allocator 용량은 추가됩니다.
- `enable_thinking=False` 프롬프트는 빈 thought 채널을 미리 포함합니다. 18개 입력의 라벨 단일 토큰 및 프롬프트 경계 검증을 통과했습니다.

## 기본 CUDA 경로의 실패

모든 파라미터를 `cuda:0`에 배치한 로딩은 17.264초에 완료됐습니다. CPU 분할이나 `hybrid-cuda`를 사용하지 않았습니다. CT 최상위 훅이 첫 forward에서 모델 전체를 BF16으로 역양자화하는 도중 `model.language_model.layers.27.mlp.down_proj`에서 CUDA OOM이 발생했습니다. 191개 quantized 모듈을 처리한 뒤 226MiB 추가 할당이 실패했고, 해당 오류 기록 시점의 PyTorch CUDA 할당은 약 16.731GiB였습니다.

실패 전에 기록한 Windows 표본에서는 전용 GPU 메모리 5,817,815,040바이트, 공유 GPU 메모리 13,706,985,472바이트, 총 committed GPU 메모리 19,524,800,512바이트였습니다. 공유 메모리가 실제 사용됐으며, 이 표본은 최대치가 아닙니다. PyTorch 할당과 Windows 카운터는 집계 범위가 다릅니다. 모델 클래스 미지원이나 라벨 인코딩 실패로 중단된 것이 아닙니다.

## 압축 유지 진단 경로

[실행 스크립트](../scripts/probe_ct_w4a16.py)는 모든 packed Linear 모듈이 symmetric INT4, group size 32, weight-only 형식인지 먼저 검증합니다. 검증 후 전체 역양자화 훅을 제거하고 328개 Linear의 forward에서 packed 값을 벡터화해 펼쳐 BF16 행렬 곱을 수행합니다. BF16 가중치는 해당 호출에만 존재하고 packed 가중치는 CUDA에 유지됩니다. fused INT4 커널을 사용한 결과가 아닙니다.

작은 동일 구조 모델에서 CT 라이브러리의 역양자화 경로와 선택지 logits이 일치했습니다. Linear 단위 float32/BF16 비교 테스트에서는 bias와 배치 입력을 포함해 결과가 정확히 일치하고, 두 번 호출한 뒤에도 packed 가중치가 유지됐습니다. group size 64는 훅을 제거하기 전에 거부합니다.

실제 12B에서도 CT 라이브러리를 층별로 호출하는 느린 방식으로 기본 예제 1건이 완료됐습니다(244.007초). 벡터화 경로의 같은 입력 logits 및 프롬프트 해시가 정확히 일치했습니다. 느린 방식은 두 번째 입력 실행 중 중단하고 벡터화 경로로 전환했습니다.

- 로딩: 15.642초.
- 기본 예제 2건 + 스트레스 16건: 18/18건 완료, 오류 없음.
- 기본 예제 결과: `account`, `billing`.
- 스트레스 기대 답 일치: 16/16건. 작은 고정 평가 세트의 결과입니다.
- 첫 추론: 20.898초. 전체 18건 중앙값: 24.750초.
- 로딩부터 전체 완료: 469.678초.
- 추론 후 CUDA 할당: 7.704GiB. 최대 CUDA 할당: 10.509GiB.
- Windows 실행 중 표본: 전용 5,844,615,168바이트(5.443GiB), 공유 5,985,271,808바이트(5.574GiB), 총 committed 11,829,886,976바이트. 최대치가 아닙니다.
- 전체 테스트: 28개 통과. `uv lock --check`, `git diff --check` 통과.
- 저장한 `scripts/probe_ct_w4a16.py`로 실제 체크포인트의 첫 예제를 다시 실행했습니다(20.894초). 평가 실행과 모델 리비전, 선택지 logits, 선택 결과, 프롬프트 해시, 입력 토큰 수가 정확히 일치했습니다.
- 실제 장치 검증은 Windows CUDA에서 수행했습니다. macOS MPS 실행은 검증하지 않았습니다.

## 재실행

스크립트 기본값은 위의 12B 체크포인트와 고정 리비전입니다.

```powershell
uv sync --locked --extra hf --extra qat
uv run --locked --extra hf --extra qat python scripts/probe_ct_w4a16.py --device cuda --input examples/stress-challenges.jsonl --output results/12b-qat.jsonl --events results/12b-qat-events.jsonl
```

실험용 runner에 한정된 방식입니다. 일반 `oev --model ... --device cuda`는 여전히 기본 CT 전체 역양자화 경로를 사용합니다.

로컬 기록: 기본 경로 `results/gemma4-12b-qat-cuda-events.jsonl`, 벡터화 경로 `results/gemma4-12b-qat-vectorized-cuda-events.jsonl`, 18건 출력 `results/gemma4-12b-qat-vectorized-cuda.jsonl`, 메모리 표본 `results/gemma4-12b-qat-vectorized-windows-memory.json`. 이 결과 파일들은 `.gitignore`에 따라 로컬에 보관됩니다.

아래 채점 표의 정답 문자는 기존 평가 데이터의 대문자 위치 메타데이터이며, 실제 oev 프롬프트에는 소문자 라벨이 사용됐습니다.
